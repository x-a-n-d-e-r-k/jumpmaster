# Crew Chat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the owner a chat inside the app that answers questions about the whole install and, on the owner's word, acts through the server's own guarded paths. Slice 1 adds a backlog queue that needs no chat at all.

**Architecture:**
- **Chat service.** A new compose service, `chat`, runs the trooper image with a second entry point (`apps/trooper/src/chat/`). Per turn it fetches each zone's default branch into a root-owned mirror and runs `claude -p … --resume` as the agent uid. Its only way to act is the server's MCP endpoint `/mcp/chat`.
- **Server.** The server owns threads and messages (SQLite) and the per-turn chat token. It relays the turn's events to the browser over server-sent events. Every action goes through the code the HTTP routes already use, as a new principal `via: 'chat'`, and the server records it as a card.
- **Goal changes.** The server commits GOAL.md on a branch through the forge API and opens a PR. It approves and merges only after the owner confirms the exact head in the browser.

**Tech Stack:** TypeScript (Node 24, ESM), vitest, Fastify (`inject` harness), better-sqlite3 migrations, zod, `@modelcontextprotocol/sdk`, Docker Compose, the Claude Code CLI already in `images/trooper`.

**Spec:** `docs/superpowers/specs/2026-11-18-crew-chat-design.md` (epic #336). The code map was taken at `origin/main` aac2dae.

## Rulings (where the design was silent or the code differs)

1. **R1 `/mcp/chat`.** `/mcp` is registered only with `mcp.enabled`, and setup must not gain a step. So chat tokens use a separate route, `POST /mcp/chat`, which is always registered and accepts chat tokens only. `/mcp` refuses chat tokens. `/mcp/chat` gets its own route class, which skips the Host check the way stick routes do: the service reaches it as `jumpmaster:7420`. It requires the bearer token and refuses any `Origin`.
2. **R2 Chat tokens.** They live in `mcp_tokens` with `scope = 'chat'`, so the `mcp_audit` foreign key, the budgets and pruning all keep working. Each row carries `chat_thread_id`, `chat_message_id` and `session_hash`, so "mcp_audit rows carry the thread and message" holds through `token_id`. The audit `detail` stays reason codes only, because the budget queries match it exactly. `listMcpTokens` hides chat tokens.
3. **R3 Read credential.** The design says the chat service holds no GitHub write credential, so there is no author-token fallback (controller ruling, overriding the drops' `githubReadToken ?? githubAuthorToken`). A PAT zone uses `githubReadToken`. An app-reviewer zone gets `appTokens.fresh(zoneId,'reviewer','drop-read-reviewer')`, revoked after the fetch. A zone with neither still chats, but without its code: the turn marks it `unavailable`, the chat says so, and the doctor check (Task 11) names the missing read token. Setup already asks for a read token, so a normal install gains no step.
4. **R4 How the credential is passed.** The design asks for a one-shot credential helper. The trooper's `mirrorFetch` already gives the same property: the token is in git's header for that process only, root fetches into a root-owned bare mirror, and the agent clones from `file://` with no token. We reuse it.
5. **R5 Capabilities.** The design says "hardening as the `jumpmaster` service", which is `cap_drop: ALL`. But root must drop to the agent uid (`setpriv`) so that a fetch token and a running `claude` never share a uid. The `chat` service therefore drops ALL and adds back only `SETUID`, `SETGID` and `KILL`. Everything else matches the `jumpmaster` service.
6. **R6 Confirmation binding.** A pending guarded change is bound to a browser session (`Confirmations.addPending({sessionIdHash})`). The chat principal therefore carries the hash of the session that posted the owner's message. `/api/chat/*` refuses Bearer-token principals with 403.
7. **R7 Revisions.** `config_revisions.via` has a CHECK without `chat`. A chat apply records revision `via: 'ui'` with note `chat thread <t> message <m>`, and the actor goes in `control_audit.via = 'chat'`.
8. **R8 Mark an objective done.** `objectives_done.ruling_id` must name a ruling. The chat tool raises the server `objective_done` briefing (subject `objective:<key>`, option `done` → `advance_objective`) and rules it with `ruleBriefing`. The next pass applies it, exactly as a browser ruling would.
9. **R9 Retry a parked item.** This puts the zone's `retryLabel` on the item's issue, through the same `set_labels` op the server uses. `syncParked` then calls `retryParkedItem`.
10. **R10 Synchronous tools.** `callTool` runs tools inside one `db.transaction`. Tools that call the forge or `ConfigStore.apply` run outside it: budgets and argument parsing are checked in one transaction, the tool runs, and then it is audited (Task 9).
11. **R11 Usage.** `noteOverage` lives in `credits.ts`, not `api/sticks.ts`. It takes a drop, so the chat feeds `ingestRateLimit` only, with `RateLimitSource.dropId = 'chat:<thread>:<seq>'`. Use on usage credits therefore never starts a credits stop by itself. A turn is refused while `dispatchGate` is `'stopped'` or `'closed'`. The design names only `stopped`, but under `closed` Claude is already being refused.
12. **R12 Goal-change merge.** The flow is per work item and adopts only `agent/issue-` branches, so a goal-change PR never reaches `decide()`. A dedicated `advanceGoalChanges` posts the review and merges through the same outbox ops (`post_review`, `merge`) and the same required-check read. The design's "narrow exception" to the protected-path refusal is exactly that function. It merges only a PR the server opened, whose only changed file is the zone's `goalPath`, at the SHA the owner confirmed.
13. **R13 Goal-change confirmation.** `Confirmations` is specific to config patches. Goal changes get their own page, `/goal-changes/:id/confirm`, which reuses the confirm page's passphrase check and backoff.
14. **R14 Image.** The chat runs on the released `jumpmaster-trooper` image with `entrypoint: ["node","/opt/trooper/chat/main.js"]`. That adds no image to sign. The service ships no skills: the system prompt carries the instructions.
15. **R15 Backlog membership.** "No Jumpmaster label" means none of `readyLabel`, `retryLabel`, `crew.stagedLabel`, `triageLabel` or `triagedLabel`, and a body that is not a Jumpmaster body (`isJmIssueBody`). Intake skips issues by authors without write access (`sync.ts`), so those rows say so and get no button.

## Global Constraints

- The central server never starts containers. Only the stick mounts the Docker socket (`deploy/compose.yaml.tmpl`).
- The install has one Claude credential, `claudeToken`. The chat service "holds no secrets at rest". The server sends it "the Claude token and a short-lived chat MCP token, in the turn's process environment and nowhere else".
- "Repository credentials never reach the model's process." The `claude` process gets no GitHub credential.
- Chat egress: "the Anthropic API and the forge only".
- The `chat` service has a read-only root, no Docker socket, is reachable only on the compose network, and writes only to the volumes `chat-repos` and `chat-sessions`.
- One turn = one `claude -p … --resume <session>` process with `--output-format stream-json`. Its tools are limited to Read, Grep, Glob, read-only `git` and the MCP tools. It has no web access.
- "The chat MCP token exists only while a turn the owner's message started is running". It "is never shown to the owner or exportable".
- "There is no tool for comments or free-form issue text." Labels and closes go through the author identity and carry no text.
- Chat config changes reach `ConfigStore.apply` as `via: 'chat'`, "treated exactly like `session`": 409 pending confirmation, and 403 for browser-forbidden paths.
- `control_audit.via` gains `chat`, and `detail` carries the thread and message ids.
- Cards come "from the server's record of the action, not from the model's text". "Rulings have no Undo."
- GOAL.md is written only by the goal-change path, and only after the owner confirms in the browser.
- "An owner who has finished setup today must get a working chat with no new step."
- No secret, token or credential appears in a log line, an audit row, a stored message or an error sent to the browser.
- Plain words in the UI: name things as the owner does ("Work on it", "Undo", "Confirm").

## Review Focus

1. **A second message while a turn runs, or a tab closed mid-stream.** Expected: the message waits as `queued` and runs next, and reopening the thread replays the stored events. Pinned in Task 7 (`a second message waits for the running turn`) and Task 8 (`reopening a thread replays events after the last seen seq`).
2. **The chat service is down, restarts mid-turn or never answers.** Expected: the message ends `failed` with a plain reason, the token is revoked, the read tokens are released and the thread stays usable. Pinned in Task 7 (`a dropped stream fails the message and revokes the token`).
3. **A backlog issue by an author without write access.** Expected: "Work on it" is not offered, because intake would skip it, and the row says why. Pinned in Task 1 (`an untrusted author's issue is listed as not startable and queue refuses it`).
4. **Undo after someone else changed the same thing.** Expected: Undo refuses with "changed since" and writes nothing. Pinned in Task 14 (label) and Task 15 (setting).
5. **GOAL.md moved on the default branch, or the PR head moved after confirmation.** Expected: no merge, and the card says to propose again. Pinned in Task 19 (`a head that moved after confirmation is never merged`).
